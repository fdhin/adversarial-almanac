# ISO 8583 payment sockets

> The card-payment protocol that your HTTP proxy will never see: after a normal REST login, POS apps open a raw TLS socket and speak binary financial frames with the processor. Authorization lives in one length-prefixed message where the merchant, terminal, amount, and card are just numbered fields you can edit.

## What it is

ISO 8583 is the message standard behind card-present money movement — the format a POS terminal, ATM, or payment app uses to ask a processor for authorization, financial capture, reversal, and settlement. Visa, Mastercard, and most acquirer networks base their interchange on it. It is not a transport: messages ride raw TCP or TLS sockets, often with a thin proprietary framing layer (a 4-ASCII-digit length prefix, a literal marker, and vendor bootstrap/auth frames before real traffic starts).

A message is three parts: the **MTI** (four digits encoding revision, message class, function, originator — `0100` authorization request, `0200` financial request, `0400` reversal, `0800` network management), a **bitmap** (8 binary bytes covering fields 1–64, whose first bit announces a second bitmap for 65–128), and the **data elements** the bitmap marks present, in strict field order with fixed or length-prefixed (`LLVAR`/`LLLVAR`) encodings. The fields that matter on an engagement: **DE2** PAN, **DE4** amount, **DE11** STAN (transaction counter), **DE37** RRN (retrieval reference — the transaction's identity), **DE39** response code (`00` = approved), **DE41** terminal ID, **DE42** merchant ID, **DE55** EMV/ICC data, **DE64** MAC.

The operator takeaway: because none of this is HTTP, the standard web-testing toolkit sees nothing — Burp shows a login and then silence while the money moves over a socket the APK hardcodes. The real authorization logic (session binding, duplicate detection, merchant scoping, terminal checks) is enforced, or not, in the processor's frame parser, which is exactly where replay, cross-tenant, and business-logic bugs live.

## The anatomy that matters on an engagement

    POS app ── REST login (JWT) ──► processor web tier            ← what Burp sees
        ▼
    raw TLS socket host:port (hardcoded in APK)
        ▼
    bootstrap: [4-digit length] + AUTH + [4-digit len] + JWT  →  AUTHOK
        ▼
    [4-digit length] + ISO 8583 frame
        = MTI | bitmap | DE4 amount | DE11 STAN | DE37 RRN | DE41 terminal | DE42 merchant ...
        ▼
    processor: session-bound? duplicate-checked? merchant-scoped?   ← every bug class lives here

Structural properties that drive findings:

1. **The socket is invisible until you read the app.** Host, port, debug toggles, and the bootstrap flow are all in the APK; nothing enumerates them from outside.
2. **Client-side identity is just fields.** Terminal ID, merchant ID, and the RRN of the transaction you are attacking are editable bytes; whether the backend re-derives them from the session is the whole test.
3. **Duplicate detection is stateful and windowed.** Replay after the dedup cache expires is a documented real-world failure mode, not a theoretical one.

## Where you'll meet it

- **Android POS terminals and soft-POS apps** — mPOS fleets, taxi/restaurant handhelds, crypto-adjacent payment apps — where one APK defines both the REST login and the payment socket.
- **Traditional terminal estates** (dial-up/Ethernet POS, ATMs) during processor-side engagements: the same message grammar, different framing.
- **Payment gateway and acquirer backends** that terminate thousands of merchant sockets — the place where cross-merchant RRN confusion becomes someone else's money.

## Reading the framework's mind

1. If payments do not appear in the HTTP proxy, do not conclude "no payment path" — grep the decompiled APK for `Socket`/`SSLSocket` usage, hardcoded processor hostnames and ports, and debug flags; the socket is the product.
2. Frames are usually length-prefixed (commonly 4 ASCII digits) and some stacks prepend a literal marker; the bootstrap (an `AUTH` frame carrying the JWT from the REST login) must be replayed before ISO 8583 traffic is accepted.
3. The MTI is the verb table: requests end in request-function digits, responses answer with the paired response MTI; a processor accepting a financial frame with a confused or mismatched MTI is itself a finding.
4. The field dictionary above is the tamper map — raise **DE4**, zero it, flip currency, swap **DE41/DE42**, forge **DE37**; watch both the ISO response and the merchant dashboard, because approvals that never reach the dashboard ("ghost transactions") are the severest form.
5. A MAC field (DE64) is integrity, not authentication — many implementations leave it absent or unenforced; its presence should change your mutations, not your plan. Workflow in the [[iso-8583-bug-bounty|methodology]].
