# X11 (the X Window System)

> A network-transparent GUI protocol from 1987 whose security model is "anyone who can read the session cookie owns the screen" — on a box where an administrator is logged into a desktop, stealing one small file means watching their screen, typing as them, and screenshotting their root terminal.

## What it is

X11 inverts what most people expect of a GUI: the **X server** owns the keyboard, mouse, and screen, and every graphical application (xterm, browser, panel) is a *client* that connects to it — locally over a Unix socket in `/tmp/.X11-unix/X<n>`, or over the network on TCP ports 6000+n (`DISPLAY=:0` is socket 0, `host:1` is port 6001 on that host). Clients authenticate to the server with a cookie (`MIT-MAGIC-COOKIE-1`) stored in the **`.Xauthority`** file of the user who owns the session — not a password, a file. `xhost` access control can additionally admit or deny by address, and `xhost +` (disabled auth) still exists in the wild.

Everything an operator cares about follows from that design:

- **The cookie IS the session.** Whatever lets you read a user's `.Xauthority` — an NFS-exported home directory, a file-read primitive, a world-readable backup, a copied home dir — lets you connect to their display as them. Real chains have lifted the cookie off an NFS-mounted home directory and replayed it on the attacker's own X client stack.
- **The server trusts all clients equally.** Any accepted client can grab the full screen, inject keystrokes, and read the clipboard — regardless of which user the *victim* applications belong to. If the logged-in desktop user is root or holds an admin terminal, the X server is a keylogger and a screen recorder aimed at it.
- **The server binary itself has been privileged.** Distributions shipped `/usr/lib/xorg/Xorg` (or `Xorg.wrap`) setuid-root so console users could start sessions — turning Xorg argument-parsing bugs into direct root.

## The anatomy that matters on an engagement

    X client (app) -- connects --> X server (owns screen+input of DISPLAY :0)
        auth: cookie from ~/.Xauthority (MIT-MAGIC-COOKIE-1) [+ xhost ACLs]
        transport: /tmp/.X11-unix/X0 (local) | TCP 6000+n (network) | ssh -X tunnel
    display manager (xdm/gdm/LightDM): XDMCP (UDP/177) — network session negotiation
    privileged helper: setuid Xorg / Xorg.wrap (legacy single-card setups)

## The two attack surfaces

### 1. Session hijack (cookie theft + impersonation)

The dominant pattern, and the reason to enumerate X even on servers (a desktop login on :0 with an administrator's terminal open is common on "workstation" targets):

- **Find a live display**: `w` shows each logged-in user's display in the FROM column (`:0` means a local GUI session); `ps aux | grep -i xorg` confirms the server and its `-auth` path; `/tmp/.X11-unix/` sockets enumerate displays; ports 6000–6063/tcp exposed mean network-reachable X (test with `xdpyinfo -display host:0` — it answers before auth on misconfigured `xhost +` boxes).
- **Steal the cookie**: locate `.Xauthority` files (home directories, NFS exports of them, `/root`-adjacent backups, dotfile archives). Transport is trivial — base64 the file, move it, decode.
- **Become the session**: point the environment at it (`export XAUTHORITY=/tmp/.Xauthority`, `export DISPLAY=:0`) or merge with `xauth add`. You now speak as the session owner.
- **Harvest**: `xwd -root -display :0 > screen.xwd` dumps the current screen (convert with ImageMagick to PNG); keystroke loggers and input-record tooling capture passwords as they are typed; clipboard tools read whatever the user copied (credentials included); input injection drives their terminal.

A real chain of exactly this shape: an NFS export exposed a desktop user's home, the `.Xauthority` in it was replayed by the attacker, `w` identified the live display, and an `xwd` screenshot of the root-privileged session captured what the administrator was doing on screen — full session compromise without touching a single password.

### 2. Privileged X server binary (CVE-2018-14665, upstream-verified)

Where `Xorg` is installed setuid-root and startable by a console user (classic distributions, some appliances):

- Versions **1.19.0 – 1.20.2**; fixed in **1.20.3** (X.Org advisory, October 2018; regression introduced by the 1.19.0 "dangerous options" checks).
- `-modulepath` — point the server at an attacker-controlled module directory: modules load into the privileged process → code execution as root.
- `-logfile` — arbitrary file overwrite with partially controllable content (font-path text is logged); overwriting `/etc/shadow` with an injectable line is the classic escalation.
- Precondition check: `ls -l /usr/bin/Xorg /usr/lib/xorg/Xorg.wrap` for the setuid bit, and whether unprivileged users can reach a console. Modern distros use logind-managed servers and dropped the bit — treat this as a legacy/appliance privesc that is verified, not assumed.

### XDMCP (the display manager's own network protocol)

XDMCP (UDP/177) lets an X server *ask a display manager for a login session* — historically to boot thin clients into full desktops. On a target with UDP/177 open, an attacker can request a session against a chosen account (`X -query host` or XNest-style), effectively gaining an interactive desktop on the target's terms; misconfigured managers have accepted sessions without sane source restrictions, and broadcast-query mode advertises every willing host on the segment. It is also pure enumeration surface: the manager's responses confirm GUI infrastructure and version-era even when nothing else is exposed.

## Where you'll meet it

- **Engineer/admin workstations** with auto-login or long-lived desktop sessions — the highest-value cookie on the box belongs to the person with a root terminal open.
- **NFS-exported home directories**: the file that authenticates the GUI travels with the home dir; any user whose home is exported hands their session to anyone with read access.
- **Legacy multi-user Unix hosts and appliances**: setuid Xorg binaries, TCP 6000 listeners with `xhost +`, XDMCP enabled for thin clients.
- **SSH jump setups**: `X11Forwarding yes` plus stolen cookies on the bastion compose into display access on hosts the user graphical-logins to.

## Reading X's mind

1. **`w` and `/tmp/.X11-unix/` are the cheap first sweep** — they name the live displays before you touch anything.
2. **`.Xauthority` is a credential file** — treat every read primitive that can reach a home directory as potential session theft.
3. **Auth and ACL are separate**: the cookie gates the connection, `xhost` gates the address; either being broken is a different finding.
4. **The X server trusts all clients** — screen capture, keylogging, and injection are features, not exploits, once you are connected.
5. **Setuid Xorg is a version-gated privesc** (1.19.0–1.20.2) — check the bit and the advisory range before promising root.
